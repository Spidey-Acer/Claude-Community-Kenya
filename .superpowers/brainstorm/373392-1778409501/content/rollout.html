How Karibu degrades safely and how it ships safely.

Fallback chain · the user is never blocked from entering

Degradation ladder · top = ideal, bottom = worst case
L1 ✓
Full Karibu
Streaming Claude conversation, tool calling, real recommendations
Happy path. ~95% of visits.
L2 ⚠

Show skeleton loader → if 5s timeout hits, abort and switch to L3

L3 ⚠
Scripted chip wizard
3-step pre-written flow, no API calls. Same chips, no free text. Tool call faked client-side. Visually identical.
API timeout, rate limit hit, cost ceiling, daily budget exhausted.
L4 ✗
Static welcome + Skip
"Welcome to CCK — explore the site, personalize anytime." Single button to dismiss. No data captured.
JS disabled, cookies disabled, all chip wizards fail.
L5 ✗
No modal at all
SSR'd page renders normally with default audience=dev (current behavior).
Server-side feature flag killed Karibu entirely.
Invariant: at every level, the user can reach the homepage in <1 click. Karibu is never a wall.

Rollout · 4 phases, ~3 weeks

Phased rollout with kill switches at every gate
Week 0
Internal flag-gated
Deploy with KARIBU_ENABLED=false. Team accesses via ?karibu=1. Walk all 5 audience flows.
Gate: all 5 flows complete clean
Week 1
10% canary
Hash-mod cookie ID; 10% of new visitors see Karibu. 90% see current modal. Monitor: completion rate, errors, latency, cost/day.
Gate: completion ≥60%, p95 <3s, errors <1%
Week 2
50% A/B test
A: Karibu. B: current PersonaSelectorModal. Measure delta on Discord join rate, application rate, bounce.
Gate: Karibu beats control on Discord join by ≥15%
Week 3
100% rollout
All new visitors get Karibu. Old PersonaSelectorModal becomes "Skin/Vibe" toggle in navbar (Section 1).
Kill switch: KARIBU_ENABLED=false reverts instantly
Abuse & security defenses
Threat Defense
Prompt injectionHardened system prompt with XML-delimited user input; tool call schema is enum-constrained (Claude can't output garbage); 300 char/msg cap; output filter strips URLs/commands from user-quoted text.
Cost runawayPer-conversation: 1500 max output tokens, 8-message hard cap, 1 tool call max. Per-IP: 5 conversations/hour. Per-day: $50 spend cap with auto-fallback to L3 scripted.
Bot abuseRate limit (Upstash). Honeypot hidden field on skip endpoint. CSRF origin check (already in /api/chat). Karibu BotID via Vercel BotID later if needed (out of v1 scope).
PII leakageSystem prompt instructs Claude not to ask for or store sensitive info (health, religion, politics). Conversation transcripts purged after 30 days. Optional fields only saved on user-volunteered consent.
Audience-shoppingSame IP starting 3+ onboardings/hour with different audiences → audit log flag. Not blocked, just logged for review.
Monitoring & observability
  • Structured logs from /api/karibu: conversation_id, latency_ms, total_tokens, audience_extracted, success_flag, fallback_level (L1-L5).
  • Admin dashboard widget: today's onboardings, completion %, audience breakdown bar chart, avg latency, cost so far this month.
  • AuditLog entry for every completed onboarding (reuses existing model).
  • Sentry for errors with context: which fallback level kicked in, which message # failed.
  • Anthropic console budget alert: $40/day warning, $50/day cap (Karibu API key isolated from /api/chat).
Explicitly OUT of v1 scope (defer to v2 or later)
  • Full Swahili conversation mode (the greeting "Karibu" is the only Swahili in v1)
  • Voice input
  • Persistent identity across cookie clearing (fingerprinting — privacy-sensitive)
  • AI-generated personalized email follow-ups
  • A/B testing different system prompts (Statsig/PostHog later)
  • Runtime LLM-powered recommendations (v1 uses pure-function ranking)
  • Auto-prompt for re-onboarding on life changes (manual footer link is enough)
  • Vercel BotID integration (add post-launch if abuse appears)
